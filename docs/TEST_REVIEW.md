# 隔离测试与深化评估

这是优化前的审计记录。后续已按本文第一阶段及部分第二阶段建议实施，当前结果见 [OPTIMIZATION.md](OPTIMIZATION.md)。

验证日期：2026-10-30，最终运行约 10:15（Asia/Shanghai）。
结论：当前有可运行的同步保护和诊断基础，但仍应定位为可靠性加强的原型。
下一步先深化同步状态机与诊断验证方法，再展开 PR/worktree 功能。

## 隔离方式与结果

本次使用独立 PTY 测试进程；测试 Shell 为 `zsh -dfc`，HOME、ZDOTDIR、XDG_CONFIG_HOME、TMPDIR 均指向临时目录。
环境变量从受控白名单构造，禁用用户/系统 Git 配置，使用私有 Git 配置和空模板，仅允许 file Git 协议。
没有修改用户 `.zshrc`、安装插件到用户环境、调用用户仓库 remote 或在其他终端中 source 插件。
测试前后 `.zshrc`、`.zshenv`、`.zprofile`、`.zlogin`、`.gitconfig`、`.config/git/config` 的文件内容指纹一致。

- Python 3.12.4、Git 2.45.2、Zsh 5.9，macOS。
- 最终 50 项自动化测试通过，约 29.18 秒（unittest 内部报告）。
- Zsh 语法与实际加载测试通过；Enter 绑定保持原值，停用后可调用原生 Git。
- 独立测试配置保持不变，临时 HOME 和测试仓库在进程退出时清理。
- 网络错误分类仍以模拟错误测试；本次没有验证真实网络、代理或服务器故障。
- Linux、Python 3.10/3.11 和更多 Git 版本仍未在本轮实测。

复现：`python3 scripts/test_isolated.py --measure`。
结构化结果见 [validation-results.json](validation-results.json)；原始日志路径也记录在其中（临时文件可能被系统清理）。

## 本轮发现并修复的问题

第一轮隔离运行有 3 项测试失败，因为测试默认 Git 模板会创建 hooks 目录。
修正夹具，显式在临时 clone 中创建 hooks 目录后，测试不再依赖用户/系统模板。
这也说明此前“测试通过”没有充分证明环境独立性。

新增的对抗测试最初还复现了 3 个产品缺口，均在临时仓库中完成：

| 问题 | 复现结果 | 本轮修复 |
| --- | --- | --- |
| `submodule.<name>.ignore=all` 隐藏子模块修改 | 原先 require_clean 误判为干净 | 同步前后检查显式指定 `--ignore-submodules=none` |
| 自定义驱动在最终预演期间改动工作区 | 原先仍会尝试 merge | 预演后重新检查工作区、HEAD、upstream、配置，变化则拒绝 |
| ignored 文件与远端新增文件重名 | 本机 ort 分叉合并中，仅 `--no-overwrite-ignore` 未保护该文件 | 比较 before→预演结果树的新增路径，显式拒绝已有内容/目录重叠和符号链接祖先 |

额外覆盖确认期间创建 ignored 文件的情况，确保最后一轮检查仍能阻止覆盖。
保留原生保护选项，但不再将它作为唯一保护依据。
[Git merge 文档](https://git-scm.com/docs/git-merge) 对该选项描述了预期行为；本报告仅记录本机复现，不推断所有版本/策略都有相同现象。

这些检查仍无法消除任意外部进程在检查后写入文件的竞态，也不是自定义驱动/hooks 的执行沙箱。
对已有目录或符号链接的某些合法目录/文件转换，本轮选择保守拒绝；未来应通过隔离预演和更精确的路径模型完善。

## 实测开销

测量使用本地 bare remote、两个临时 clone，不计用户阅读/确认等待。
调用数是助手直接发起的 Git 进程数，不包括 Git 内部自行启动的子进程。
每个场景仅运行一次，以下用于定位架构问题，不是跨环境性能基准。

| 场景 | 生成计划调用数/耗时 | 执行调用数/耗时 | 总调用数/耗时 |
| --- | --- | --- | --- |
| 快进 | 27 / 0.3479s | 42 / 0.4794s | 69 / 约 0.83s |
| 干净分叉合并 | 28 / 0.3402s | 46 / 0.5341s | 74 / 约 0.87s |

两者均读取配置 14 次、运行 status 8 次；rev-parse 分别 23/24 次。
保护检查有实际作用，但当前实现重复查询较多。若额外施加“每次启动 250ms”的假设成本，
仅启动附加成本就可能为 17.25/18.5 秒——这是敏感性模型，**不是本机观测到的运行时间**。
因此现阶段优先减少跨进程调用；改写语言并不能直接消除这类开销。

## 深化顺序与验收条件

### 第一阶段：同步状态机、故障恢复与查询成本

1. 引入明确的 RepositorySnapshot：用批量 Git 输出采集 HEAD、分支、工作区、upstream 等状态。
   同一验证阶段复用快照，确认后必须重新采集，不能跨确认时间缓存安全判断。
   保持 Git 自身解析 refspec/push 语义，不用手写字符串规则替代 Git。
2. 为每次状态转换设计可重复的故障注入点：保存意图前后、创建备份引用前后、原生 merge 返回前后、最终记录前后。
   真正 SIGKILL 子进程，而不只模拟 KeyboardInterrupt；重新启动后应能解释记录与实际状态是否一致。
3. 增加只读 reconcile：区分“Git 已完成但日志未落盘”“有匹配的未完成 merge”“分支已被外部推进”“证据不足”。
   证据不足不得自动 reset、自动继续或覆盖引用；重复运行应得到稳定结果。
4. 增加路径保护矩阵：ignored 文件/目录、符号链接、子模块、文件与目录互换、稀疏检出、重命名、二进制、大小写差异。
5. 维护可重放随机仓库场景，验证数据保护不变量，而不只是固定示例或与实现结构相同的断言。

建议验收目标：在保持负面场景拒绝能力的前提下，快进直接 Git 调用数降至 25 以内；
每个持久化转换点均有实际终止/重启测试，引用、索引和文件内容的预期行为明确。
这比追加 rebase 开关更优先。rebase 必须等隔离逐提交预演、提交映射和失败恢复成熟后再加入。

### 第二阶段：从“提示候选原因”到可验证的诊断实验

1. 建立有已知原因的故障场景：慢文件扫描、慢 hook、签名/编辑器等待、凭据 helper 等待、受控远端超时、进程启动开销。
   分类规则应使用事件类型、child_class、可执行程序等结构化证据；当前任意 argv 子串判断存在误判空间。
2. 为每条判断保留支持/反对证据，unknown 单列；用故障集测误报率和漏报率，不能把启发式 confidence 当作概率。
3. 引入诊断调度：按成本和预期信息量选择下一探测，避免对每个问题都重复运行全部 status 对照。
   明确区分冷启动、热缓存和样本不足，基线附带 Git 版本、平台及测量方式。
4. 优化实验先在隔离环境中临时应用配置，完成 A/B 对照；展示收益与适用条件后才询问是否写回仓库配置。
   不直接修改用户全局配置。
5. 做实际输出字节预算：当前 capture 的 4 MiB 是最终保留上限，临时文件写入量仍可能很大。
   未来应在运行期间检测字节数并终止超限探测，同时测量诊断自身的 CPU、I/O 和耗时开销。

建议验收目标：一份可复现的故障矩阵，报告每类命中/误报/unknown 及观察者开销；
已知故障的诊断不改变原命令退出码，不泄漏凭据，取消后不留下同进程组探测进程。

### 第三阶段：再扩展成完整工作流

- 先做只读 PR 阻塞解释，核对具体 SHA、缺失必需检查、规则和权限，信息不足保留 unknown。
- 然后做工作区初始化/失败重试/就绪/清理状态机，复用日志、快照和恢复判断。
- 最后扩展受控文件快照与恢复。现在的恢复分支只是提交恢复入口，不能恢复任意未提交文件。
  文件快照需要显式范围、大小预算、内容校验和恢复前冲突预览，不能仅换一个 undo 命令名。

## 对成品深度的判断

目前的价值是把同步预演、保护与恢复入口连接起来；短板是故障后的自动状态核对、
诊断结论的实证验证，以及大量小 Git 进程带来的架构开销。
建议下一轮只完成第一阶段，给出故障注入覆盖与调用数前后对比，再深入第二阶段。
功能数量暂时保持稳定，用可验证的行为和量化结果证明深度。
